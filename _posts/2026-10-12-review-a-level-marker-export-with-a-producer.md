A producer can tell whether an exit belongs in the upper-right corner of a level. That judgment remains useful when an agent writes the script that exports its coordinates. The awkward part is deciding what the producer's inspection establishes and what still needs an engineer.

Use a project small enough to inspect together. The example here has three markers on an eight-column, six-row grid. The exporter reads a JSON file and prints CSV. It has no engine integration, network request, production repository access, or automatic write into a game project.

## Define the coordinate contract first

The sample uses 32-unit cells. Columns and rows start at zero, the origin sits at the upper-left corner, X increases right, and Y increases down. Exported positions refer to cell centers.

The player starts at column 1, row 4. The gate objective sits at column 6, row 1. A pit hazard occupies column 4, row 4. These placements give the producer a concrete expectation: the gate is above and to the right of the player, while the pit shares the player's row.

Write those decisions into the brief before generating the script. “Export the markers correctly” leaves several conventions unresolved. A script can produce valid numbers while using corner coordinates, reversing the vertical axis, or swapping rows and columns.

The brief should also name the supported marker kinds, the expected output, and the point where the runner must stop. In this example, that point is producing the CSV and evidence for review. Importing the result into a game is separate work.

## Run a copy of the fixture

Unpack the [source kit]({{ '/assets/level-marker-review/source.zip' | relative_url }}) into a temporary working folder. It requires Node.js 20 or newer and has no npm dependencies. Run:

```sh
node export-markers.mjs sample-level.json
node verify.mjs
```

The actual first command produced:

```csv
id,kind,x,y
player,spawn,48,144
gate,objective,208,48
pit,hazard,144,144
```

The second command passed 14 checks. They include the exact CSV, edge-cell centers, input preservation, malformed identifiers, duplicate identifiers, unsupported marker kinds, and invalid coordinates. An actual CLI run against the out-of-grid fixture exited 1 and produced no partial CSV.

The exporter builds all output before sending it to stdout. It deliberately does not create a target file. A runner can inspect the terminal output before choosing where to save it. Run it with your own authorized tools and the supplied sample data; a teammate's account or token is not part of the handoff.

## Give a qualified engineer the code questions

The center conversion is only two lines:

```javascript
const x = (marker.column + 0.5) * level.tileSize;
const y = (marker.row + 0.5) * level.tileSize;
```

An engineer should confirm that this convention matches the intended importer. They should also examine input validation, error handling, coordinate bounds, and output formatting.

One concrete technical-review finding was JavaScript coercion: a regular-expression check alone can accept an array whose string conversion looks like a valid identifier. The supplied script now requires a string before testing the identifier pattern, and a regression case rejects an array-valued ID. Identifier restrictions also exclude commas, newlines, and spreadsheet formula prefixes from this CSV field.

The input-size check has an explicit limitation. It runs after `readFile`, so it prevents oversized input from being exported but does not bound the memory used to read it. This trusted local sample is not an untrusted upload service. A specialist must revisit file intake before that deployment.

These are AI technical-review notes. Independent qualified human code review remains pending. An engineer's review should be recorded before adopting the script in a studio toolchain, together with importer tests and any changes they require.

## Name who decides each part

The preparer defines the level intent, coordinate convention, expected CSV, evidence, and stopping point. The runner executes the bounded task with their own authorized coding tools and returns the script, output, checks, and limitations. The qualified engineering reviewer judges technical suitability. The producer judges the requested placement and accepts or requests rework within that agreed scope.

That division fits [Wagglet's approach to meaningful human–AI work](https://wagglet.com/blog/meaningful-work-with-human-ai-pairs). In a game studio AI workflow, a non-programmer's contribution can be specific and consequential without turning a visual inspection into a claim of engineering expertise.

Before accepting this example, check the three placements, reproduce the CSV, inspect the rejected-input case, and record the engineering review. Preserve the distinction between accepting a delivery and authorizing an engine integration or deployment.
